# VM entry/exit и цикл KVM_RUN

## Где исполняется гость

На Intel аппаратная виртуализация разделяет VMX root operation и VMX non-root
operation. Это дополнительное измерение к уровням привилегий CPL: гостевое
ядро может работать в ring 0, оставаясь под контролем гипервизора.

В обычном запуске KVM находится в ядре Linux, а minivmm — процесс userspace.
Процесс вызывает `ioctl(vcpu_fd, KVM_RUN, 0)`, после чего KVM подготавливает
состояние vCPU и выполняет вход в гостя. Системный вызов и аппаратный VM entry
— разные переходы: сам minivmm инструкций VMX не выполняет.

У Intel запуск и продолжение гостя используют `VMLAUNCH` и `VMRESUME`.
Их архитектура, VMCS и проверки состояния описаны в разделах VMX руководства
[Intel SDM, Volume 3](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html).

## Что переключает процессор

VMCS задаёт guest state, host state и execution controls. При VM entry
процессор проверяет допустимость конфигурации, загружает предусмотренные
архитектурой поля гостя и начинает его исполнение с гостевого RIP.
Controls определяют, какие события требуют VM exit.

При VM exit процессор сохраняет предусмотренную часть гостевого состояния,
фиксирует причину выхода и передаёт управление точке входа гипервизора
с настроенным host state. Это не сохранение всех регистров одним действием:
для RIP/RSP есть специальные поля VMCS, а остальные общие регистры KVM
сохраняет и восстанавливает программно. Состояние FPU/XSAVE имеет отдельный
механизм переключения.

В minivmm начальное состояние задаётся через KVM API в
[`cpu_setup.c`](../../src/x86/cpu_setup.c); настройкой VMCS занимается KVM.
Для диагностики VMM читает доступное через API состояние с помощью
`KVM_GET_REGS` и `KVM_GET_SREGS`.

## Аппаратный выход и возврат в minivmm

VM exit не обязательно завершает `KVM_RUN`. KVM может обработать событие
в ядре и снова войти в гостя. Например, ответы на `CPUID` берутся из
настроенной через `KVM_SET_CPUID2` таблицы: отдельный обработчик CPUID
в userspace-цикле minivmm не нужен.

Если требуется обработка в userspace, KVM возвращает управление из
`KVM_RUN` и заполняет общий mmap `struct kvm_run`. Его `exit_reason` —
причина возврата по API, а не необработанное аппаратное поле VMCS.
Форматы выходов описаны в
[KVM API: The kvm_run structure](https://docs.kernel.org/virt/kvm/api.html#the-kvm-run-structure).

В [`vcpu.c`](../../src/vcpu.c) текущие действия такие:

| Выход | Действие minivmm |
|---|---|
| `KVM_EXIT_IO` | Байты OUT в порт `0x3f8` идут в stdout; неизвестный IN получает `0xff`. |
| `KVM_EXIT_MMIO` | Запись логируется; для чтения заполняется `mmio.data` значением `0xff`. |
| `KVM_EXIT_HLT` | Возврат `VCPU_STOP_HLT`; `main.c` завершает процесс с кодом 0. |
| `KVM_EXIT_SHUTDOWN` | В наших тестах это triple fault; завершение с ошибкой и дамп регистров. |
| `KVM_EXIT_FAIL_ENTRY` | Лог аппаратной причины неудачного входа и дамп регистров. |
| `KVM_EXIT_INTERNAL_ERROR` | Лог внутренней ошибки KVM и дамп регистров. |

Завершение по `HLT` — соглашение текущего VMM без irqchip. После появления
прерываний остановленный vCPU должен иметь возможность продолжить работу.

## Почему после MMIO нужен следующий KVM_RUN

При чтении MMIO userspace заполняет `run->mmio.data`, но гостевой регистр
ещё не обязательно содержит результат. KVM завершает операцию при следующем
`KVM_RUN`; то же требование завершения относится к PIO. Это явно оговорено
в [описании MMIO/PIO в KVM API](https://docs.kernel.org/virt/kvm/api.html#the-kvm-run-structure).

Поэтому обработчик заполняет ответ и возвращается в цикл, а гостевой payload
после возобновления сравнивает прочитанный байт с `0xff`. Это также важно
для будущего snapshot: сразу после выхода MMIO состояние ещё может содержать
незавершённую операцию.

Если `KVM_RUN` вернул `-1` с `errno == EINTR`, текущий цикл повторяет вызов
без диспетчеризации `exit_reason`. Управляемая остановка по сигналу остаётся
задачей этапа с `immediate_exit`.

## Исключения внутри гостя

Исключение не обязано возвращаться в minivmm. Real-mode payload с `ud2`
использует собственный обработчик `#UD` в IVT. В long-mode payload IDT пока
пуста: `ud2` в ветке FAIL не удаётся доставить, доставка исключений
эскалирует до triple fault. VMM получает `KVM_EXIT_SHUTDOWN` и возвращает 1.
Это позволяет тесту отличать провал самопроверки от успешного `hlt`.
