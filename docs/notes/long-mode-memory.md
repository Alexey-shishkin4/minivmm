# Long mode и identity mapping

## Какие адреса используются

| Адрес | Смысл |
|---|---|
| GVA | Виртуальный адрес гостя; после сегментации — linear address для paging. |
| GPA | Физический адрес с точки зрения гостя. |
| HVA | Виртуальный адрес памяти в процессе VMM, полученный через `mmap`. |
| HPA | Физический адрес памяти внешнего хоста. |

В 64-битном payload базы CS/DS/ES/SS не добавляют смещение к адресу;
FS/GS могут иметь отдельные базы, но в нашей настройке они равны нулю.

Для обычного запуска с EPT аппаратная трансляция концептуально выглядит так:

```text
GVA --guest page tables--> GPA --EPT--> HPA
                           |
                      memslots + offset
                           |
                          HVA
```

Ветка к HVA показывает, как userspace VMM получает доступ к памяти;
она не является дополнительным обязательным шагом каждого аппаратного load.
Модель трансляции объясняется в
[документации MMU KVM](https://docs.kernel.org/virt/kvm/x86/mmu.html).
В nested-среде добавляется трансляция между физическими адресами L2 и L1;
с точки зрения minivmm его API и собственные таблицы остаются теми же.

## Что именно означает identity mapping

Identity mapping задаёт `GVA == GPA` на выбранном диапазоне. Это не равенство
с HVA или HPA и не отключение paging. Гостевой CPU всё равно использует CR3
и таблицы страниц, а KVM управляет следующим уровнем трансляции.

В [`cpu_setup.c`](../../src/x86/cpu_setup.c) выбран диапазон `[0, 1 GiB)`.
Для него нужны PML4, PDPT и PD; записи PD завершают обход большими страницами
по 2 МиБ, поэтому отдельная PT не создаётся.

| Диапазон GPA | Назначение |
|---|---|
| `[0x1000, 0x10000)` | Максимальный диапазон raw payload по текущему loader. |
| `[0x10000, 0x11000)` | PML4. |
| `[0x11000, 0x12000)` | PDPT. |
| `[0x12000, 0x13000)` | PD. |
| `[0x13000, 0x14000)` | Страница для GDT, используются первые три дескриптора. |
| `[0x14000, 0x18000)` | Стек; начальный RSP равен `0x18000`. |

`gpa_to_hva()` проверяет, что вся структура с таблицами, GDT и стеком
помещается в одном RAM-регионе. `_Static_assert` проверяет отсутствие
пересечения с максимальным диапазоном payload.

## Ручной разбор таблиц

Начальные значения до того, как CPU мог установить Accessed/Dirty:

```text
CR3      = 0x10000
PML4[0]  = 0x11003  -> PDPT at GPA 0x11000
PDPT[0]  = 0x12003  -> PD at GPA 0x12000
PD[i]    = (i << 21) | 0x83
```

`0x03` означает Present и Read/Write. В `0x83` также установлен Page Size:
запись PD указывает на страницу 2 МиБ. User/Supervisor равен нулю,
поэтому отображения предназначены для supervisor-кода.

Для GVA `0x00200123`:

- индекс PML4: биты `[47:39]` равны 0;
- индекс PDPT: биты `[38:30]` равны 0;
- индекс PD: биты `[29:21]` равны 1;
- смещение внутри страницы: биты `[20:0]` равны `0x123`.

`PD[1] = 0x200083` задаёт базу `0x200000`. Прибавляем смещение:
`GPA = 0x200000 + 0x123 = 0x00200123`. Поэтому этот участок отображается
тождественно. 512 записей PD покрывают `512 * 2 MiB = 1 GiB`.
Гостевые страницы по 2 МиБ сами по себе не гарантируют huge pages на хосте.

## Как включён 64-битный режим

Начальное состояние согласовано: `CR0.PE|PG`, `CR4.PAE`, CR3 с GPA PML4,
`EFER.LME|LMA`, кодовый сегмент с `CS.L=1` и `CS.DB=0`.
CPUID сообщает поддержку long mode, но сам по себе режим не включает.

На физическом CPU загрузчик выполняет последовательность переключения
регистров и сегментов. Здесь VMM задаёт уже готовый образ через
`KVM_SET_SREGS`; LMA передаётся как часть этого образа, хотя при обычной
работе CPU он отражает активность режима, а не является свободно
записываемым переключателем. Архитектурные условия описаны в
[Intel SDM, Volume 3: IA-32e mode и paging](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html).

GDT находится в памяти гостя, а кэшированные дескрипторы сегментов отдельно
заданы в `struct kvm_segment`. Одной записи GDT в RAM недостаточно.
RIP получает `0x1000`, RSP — вершину стека, IF и DF сброшены.
Настройка рассчитана на свежий vCPU и небольшой assembly payload.

## Почему отображение не создаёт RAM

В [`longmode_hello.S`](../../guest/payloads/longmode_hello.S) используется
адрес `0x200000`, а тест запускает VMM с `--mem 1M`. Гостевые таблицы
успешно переводят GVA `0x200000` в GPA `0x200000`, но этот GPA не входит
в RAM memslot. Для наших byte load/store KVM возвращает `KVM_EXIT_MMIO`.
minivmm логирует запись `0x42`, а на чтение отвечает `0xff`.

Это отличается от отсутствующей записи в гостевых таблицах: в таком случае
возникнет гостевой `#PF`. У текущего payload нет IDT для обработки исключений,
поэтому такой fault может закончиться triple fault.

Если запустить тот же payload со стандартными 128 МиБ RAM, `0x200000`
окажется обычной памятью. Чтение вернёт записанное `0x42`, и проверка MMIO
правильно завершится веткой FAIL.

Текущие ограничения: один vCPU, supervisor-код, первый 1 ГиБ виртуального
пространства, без обработчиков исключений и подготовки Linux boot protocol.
